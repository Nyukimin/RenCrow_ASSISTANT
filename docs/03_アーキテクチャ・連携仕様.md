# アーキテクチャ・連携仕様

## runtime構成

primary runtimeはGo binary `rencrow-assistant`です。利用者環境ではbinaryと設定
ファイルで起動できる形にし、LLMや端末固有SDKをserverの必須演算依存にしません。

```text
           RenCrow_CMD (planned launcher)
                        |
                        v
                 RenCrow_ASSISTANT
 +--------------------------------------------------+
 | Household / Preferences / Permissions            |
 | Shortcut / Routine Registry / Routine Scheduler   |
 | Connector Orchestration / Result Cache            |
 | Delivery Router / Ack / Snooze / Retry            |
 | CORE Client / Device Sessions / Public API        |
 +--------------------------------------------------+
          |                    |                 |
          v                    v                 v
    RenCrow_CORE          RenCrow_PORTAL      Device clients
    complex tasks         Web Viewer          Stack-chan/watchOS
```

初期実装では実際のcallerと変更境界に沿ってpackageを分けます。将来利用を理由に
registry、adapter、protocol階層を先行して乱立させません。

ニュースは共通News／Knowledge基盤の取得結果を優先して参照します。共通基盤が未実装の
移行期間にASSISTANTが取得を代行する場合も、X、Reddit、報道RSS/APIの認証、rate limit、
response schemaはproviderごとの薄いadapterへ隔離します。Routine schedulerはprovider
APIを直接呼ばず、connector orchestrationが取得、正規化、鮮度判定、source単位の
degraded状態をまとめます。共通corpusの重複排除と時系列、利用者別の選定・既読・配信を
同じstoreへ混在させません。Xは公式API、Redditは許可された公開APIまたはOAuth経路を使い、
規約回避を目的としたscrapingを実装しません。

## Interaction profile

ASSISTANTはPORTALやCMDと別の会話runtimeを持たず、RenCrowの共通Interaction意味論を
proactiveな入口とDeviceへ適用します。

CORE requestには`X-RenCrow-Client: RenCrow_ASSISTANT`と
`X-RenCrow-Interaction-Profile: assistant-core`を付けます。このprofileはCORE側の
capability guard入力であり、利用者認証やDevice credentialの代替ではありません。

| 共通能力 | ASSISTANTでの利用 |
| --- | --- |
| Chat | 利用者・端末・明示Agentを付けてCOREへ送受信する |
| IdleChat | 利用者設定とDevice capabilityが許す場合に購読・操作する |
| recipient / Agent | 利用者の明示選択を維持し、別Agentへ黙ってfallbackしない |
| event / session | 再接続、重複、順序、request／response相関を扱う |
| STT / TTS | 動的会話でCORE contractを使い、端末再生結果を別に追跡する |
| Task | 必要時だけCOREへ昇格し、結果を元のdeliveryへ戻す |
| error | unavailable、degraded、denied、expired、failedを区別する |

ASSISTANT固有差は、時刻・条件発火、PUSH、User／Family／Device／Routine／Delivery状態です。
Apple Watchなど能力の小さい端末へ全Chat／IdleChat操作を強制せず、利用者scopeと
Device capabilityで公開能力を制限します。

### Interaction output

Routine通知とCORE応答は、少なくとも次の意味を保つ共通outputとしてdeliveryへ渡します。

```json
{
  "source": "assistant",
  "user_id": "user-001",
  "category": "morning_brief",
  "trace_id": "trace-001",
  "content": {
    "text": "午後は雨です。折りたたみ傘があると安心です"
  }
}
```

`trace_id`は必須です。COREから戻ったoutputはCOREの`trace_id`を変更せず、ASSISTANT内で
開始するRoutine outputはASSISTANTがroot `trace_id`を生成してDevice deliveryまで
引き継ぎます。現行foundationは`delivery_id`と`trace_id`を含むrenderer contractを
実装済みで、event ID、expiry、sensitivityなどはruntime実装時にAPI仕様とcontract
testで固定します。

## COREとの境界

ASSISTANTからCOREへ渡すのは、Agentによる対話・調査・生成・継続作業が必要な場合です。

```json
{
  "request_type": "task",
  "user_id": "user-001",
  "requested_agent": "shiro",
  "task": "通学経路への運休影響を調べる",
  "context": {
    "departure_time": "07:45",
    "usual_route": "configured-route-id"
  }
}
```

- ASSISTANTは最小限の許可済みcontextだけを渡します。
- COREはAgent、Memory、Knowledge、Task、同期policy判定、traceを所有します。
- COREの結果にはrequest / task / userの相関IDを付け、ASSISTANTが元のdeliveryへ戻します。
- COREがunavailableでも決定論的な目覚ましや既にcache済みの配信を可能な範囲で継続し、
  Agentが必要な処理は明示的なdegradedとします。
- COREへの移譲を通常Routineの必須経路にせず、Agent会話、深い調査、生成、複数工程Task
  が必要な場合だけ利用します。

### LINE PUSH transport contract

現行のLINE通知は、ASSISTANTが通知とDelivery状態を所有し、COREが既存LINE adapterを
実行する次の境界を使います。

```text
ASSISTANT Notification Service
  -> POST http://127.0.0.1:18790/internal/assistant/notifications/line
  -> CORE channels.Registry / LINE adapter
  -> LINE Messaging API push
  -> iPhone
  -> Apple Watch
```

request:

```json
{
  "delivery_id": "dly_...",
  "trace_id": "trc_...",
  "user_id": "user-001",
  "title": "RenCrow",
  "body": "通知テストです。"
}
```

ASSISTANT clientは`X-RenCrow-Client: RenCrow_ASSISTANT`と
`X-RenCrow-Interaction-Profile: assistant-core`を付けます。このendpointはCORE側でも
loopback接続だけを許可し、Tailscale Serve／FunnelやLANへ公開しません。現在は同一host上の
service間契約であり、remote配置へ変更する場合は相互認証を追加するまで利用を許可しません。

COREは`delivery_id`ごとのtransport receiptだけを
`workspace_dir/state/assistant_line_push_receipts.jsonl`へ`0600`で記録します。これは
ASSISTANT Deliveryの正本ではなく、送信完了後の応答消失やprocess restartによる重複pushを
防ぐための実行証跡です。

| CORE response | ASSISTANTの扱い |
| --- | --- |
| `200 sent, duplicate=false` | `sent`へ遷移 |
| `200 sent, duplicate=true` | 既送信として`sent`を維持 |
| `409` | 結果不明の`uncertain`。同じIDで自動再送しない |
| `400` | request不正。送信前失敗 |
| `503` | adapter、credential、送信先の準備不足。`failed` |
| `502` | 外部送信結果が不明。ASSISTANT clientは`uncertain`として扱う |

ASSISTANT側の現行clientはloopback以外のCORE URLを拒否します。LINE credential、完全な
LINE送信先ID、通知本文をDelivery JSONLへ保存しません。

## PORTALとの境界

PORTALはASSISTANTの状態の正本ではありません。ASSISTANTの公開APIを利用して、
閲覧、Routine設定、端末登録、通知履歴、Agent呼び出しなどのUIを提供します。

- 読み取りsurfaceからwrite actionを許可しません。
- write actionは利用者認証、scope、CSRF対策、idempotencyを必要とします。
- Debug、Ops、Repair、secret、他利用者のprivate dataを中継しません。
- ASSISTANT APIが未実装の現在、PORTAL連携はplannedです。
- PORTALが停止または閉じていても、ASSISTANTのscheduler、PUSH、Device sessionは継続します。

## CMDとの境界

`RenCrow_CMD`はASSISTANTの実装を内蔵せず、plannedの`rencrowctl assistant`から
`rencrow-assistant`を起動・管理します。Routine、利用者、端末、delivery状態の正本は
ASSISTANTに残し、CMDはprocess launcherと許可されたAPIのcommand facadeに限定します。

## Device contract

初期通信はHTTPとWebSocketを使います。

- HTTP: 初回登録、設定、履歴、音声・画像asset、capability更新
- WebSocket: 常時接続、PUSH、短い会話、状態、acknowledgement、入力event
- MQTT: 端末数、接続維持、電力要件から必要性が確認された場合だけ追加

端末は接続時に能力を申告します。

```json
{
  "device_type": "stackchan_mini",
  "capabilities": {
    "display": true,
    "microphone": false,
    "speaker": true,
    "servo": false,
    "touch": true,
    "haptics": false
  }
}
```

ASSISTANTは能力、利用者設定、優先順位、現在状態に応じてdeliveryを変換します。

| client | 主な表現 |
| --- | --- |
| Stack-chan | 音声、表情、首振り、タッチ、短い会話 |
| Stack-chan Mini | 短い音声、簡易表示、ボタンまたはタッチ |
| Apple Watch | 通知、振動、一画面の要点、短い応答 |
| iPhone | 通知、詳細画面、音声・文字入力 |
| Web browser | 履歴、設定、長文、出典、詳細操作 |

## Device提供形態

- Apple Watchはnative watchOS appとします。
- iPhoneはWeb/PWAで実現できる機能を優先し、必要な端末固有機能だけnative化します。
- Stack-chanは既存hostへRenCrow MODを追加する試作から始め、安定後に専用firmwareを検討します。
- Stack-chan Miniは同じcontractの縮小capability profileにします。
- 初回Wi-Fi・pairing用の端末内Web画面は許可しますが、RenCrow_PORTAL本体を端末へ複製しません。
